# Week4 Team3 Project

Vanilla JavaScript로 **pre-Fiber React 스타일의 Virtual DOM 라이브러리**를 직접 구현하고, 이를 검증할 수 있는 Demo Lab과 Benchmark 페이지를 함께 만든 프로젝트입니다.

이 프로젝트의 목적은 단순히 개념을 정리하는 것이 아니라, 브라우저의 실제 DOM이 어떻게 동작하는지 이해하고, 그 위에서 Virtual DOM과 Diff 알고리즘이 왜 필요한지 직접 구현과 실험을 통해 확인하는 데 있습니다.

## 프로젝트가 다루는 핵심 주제

이 프로젝트는 아래 질문에 답하는 방향으로 설계되었습니다.

- 브라우저는 DOM을 어떻게 다루는가
- 실제 DOM은 왜 비용이 큰가
- Virtual DOM은 어떤 구조를 가지는가
- 왜 Virtual DOM이 필요한가
- Diff 알고리즘은 어떤 방식으로 변경점을 찾는가
- React 스타일 렌더링은 실제 DOM을 어떻게 최소 변경으로 업데이트하는가

## 1. 브라우저에서 DOM을 다루는 방법: `Document`, `Window`

브라우저에서 자바스크립트가 웹페이지를 다룰 수 있는 이유는 브라우저가 전역 객체를 제공하기 때문입니다.

### `window`

`window`는 브라우저 창 전체를 나타내는 객체입니다. 브라우저 환경의 최상위 전역 객체이며, 다음과 같은 기능들을 포함합니다.

- `setTimeout`, `setInterval`
- `location`
- `history`
- `navigator`
- `document`

즉 `window`는 브라우저 실행 환경 전체라고 볼 수 있습니다.

### `document`

`document`는 현재 HTML 문서를 나타내는 객체입니다. 실제 DOM 트리에 접근하고 조작할 때 가장 많이 사용하는 객체입니다.

예를 들어:

- `document.getElementById()`
- `document.querySelector()`
- `document.createElement()`

같은 메서드를 통해 DOM 요소를 찾고, 만들고, 수정하고, 삭제할 수 있습니다.

즉:

- `window` = 브라우저 환경 전체
- `document` = 현재 페이지의 DOM 문서

라고 이해할 수 있습니다.

## 2. 실제 DOM의 변화를 감지하기 위한 브라우저 API

브라우저는 실제 DOM이 바뀌었는지 감지할 수 있는 API도 제공합니다. 대표적인 API는 **`MutationObserver`** 입니다.

이 API를 사용하면 다음과 같은 변화를 감지할 수 있습니다.

- 자식 노드 추가 / 삭제
- 속성 변경
- 텍스트 변경
- 특정 요소 하위 트리 전체 변화

즉 실제 DOM이 언제, 어디서, 어떤 방식으로 바뀌었는지 감시할 수 있습니다.

이 프로젝트에서는 성능 실험에서 실제 DOM 갱신 수를 비교하는 보조 수단으로 이런 개념을 함께 참고합니다.

## 3. 실제 DOM이 느린 이유

실제 DOM은 단순한 자바스크립트 객체가 아니라, 브라우저 렌더링 엔진과 연결된 구조입니다.

즉 DOM을 직접 수정하면 브라우저는 화면을 다시 계산해야 할 수 있고, 이 과정에서 비용이 커집니다.

### Reflow

Reflow는 요소의 크기나 위치가 바뀌었을 때 브라우저가 레이아웃을 다시 계산하는 과정입니다.

예:

- 요소 추가 / 삭제
- width, height 변경
- 폰트 크기 변경
- 텍스트 길이 변경

이 경우 주변 요소까지 위치를 다시 계산해야 할 수 있기 때문에 비용이 큽니다.

### Repaint

Repaint는 요소의 위치나 크기는 그대로지만 색상, 배경, 테두리 같은 시각적 속성만 바뀌었을 때 다시 그리는 과정입니다.

예:

- color 변경
- background 변경

보통 Reflow가 Repaint보다 더 비쌉니다.

### 왜 중요한가

실제 DOM을 반복적으로 직접 조작하면, 브라우저는 DOM 변경 자체뿐 아니라 Reflow / Repaint 비용까지 함께 부담하게 됩니다.

그래서 UI 변경이 많아질수록, 실제 DOM을 직접 계속 수정하는 방식은 성능상 불리해질 수 있습니다.

## 4. Virtual DOM

### Virtual DOM이란

Virtual DOM은 실제 DOM을 메모리 위에서 표현한 **자바스크립트 객체 트리**입니다.

즉 브라우저가 직접 관리하는 실제 DOM을 바로 수정하는 대신, 먼저 비교 가능한 트리 구조를 메모리 상에 만들고, 이 트리를 기준으로 변경점을 계산합니다.

### 이 프로젝트의 VDOM 구조

이 프로젝트에서 Virtual DOM 노드는 다음과 같은 정보를 가집니다.

- `type`: `element`, `text`
- `tag`: 예: `div`, `article`, `button`
- `attrs`: 속성 정보
- `children`: 자식 노드 배열
- `text`: 텍스트 노드 값
- `key`: 형제 노드 비교용 식별자
- `path`, `depth`: 트리 시각화와 patch 추적용 메타데이터

즉 Virtual DOM은 단순히 HTML 문자열이 아니라, 비교와 추적이 가능한 구조화된 객체 트리입니다.

## 5. Virtual DOM이 필요한 이유

Virtual DOM을 사용하는 이유는 다음과 같습니다.

### 1. 실제 DOM을 직접 계속 수정하지 않기 위해

실제 DOM은 브라우저 렌더링 비용과 연결되어 있기 때문에, 변경이 많을수록 부담이 커집니다.

### 2. 이전 상태와 새 상태를 비교하기 쉽게 만들기 위해

실제 DOM을 직접 비교하는 대신, 메모리 위의 객체 트리 두 개를 비교하면 변경점을 구조적으로 계산할 수 있습니다.

### 3. 최소 변경 렌더링을 하기 위해

전체 화면을 다시 그리는 대신, 바뀐 부분만 찾아 실제 DOM에 반영할 수 있습니다.

즉 Virtual DOM은 **실제 DOM을 대체하는 것이 아니라, 실제 DOM을 효율적으로 업데이트하기 위한 중간 비교 구조**입니다.

## 6. Diff 알고리즘

### Diff 알고리즘이란

Diff 알고리즘은 **이전 Virtual DOM**과 **새로운 Virtual DOM**을 비교하여 변경된 부분만 찾아내는 알고리즘입니다.

즉 전체 트리를 다시 렌더링하지 않고, 실제로 달라진 부분만 Patch 목록으로 분리하는 역할을 합니다.

### Diff 알고리즘을 사용하는 이유

Diff 알고리즘을 사용하는 이유는 다음과 같습니다.

- 실제 DOM 전체를 다시 그리는 비용을 줄이기 위해
- 변경되지 않은 노드는 재사용하기 위해
- 새로운 노드, 삭제된 노드, 순서 변경된 노드를 정확히 식별하기 위해
- 최소 변경 렌더링을 수행하기 위해

즉 Diff는 **Virtual DOM을 사용하는 가장 핵심적인 이유를 실제로 가능하게 만드는 단계**입니다.

## 7. Diff 알고리즘의 동작 방식

이 프로젝트의 Diff 알고리즘은 두 VDOM 트리를 비교하여 최소 변경 목록을 찾습니다.

기본 흐름은 다음과 같습니다.

1. 이전 노드와 새 노드를 비교한다
2. 노드가 없으면 생성 또는 삭제로 판단한다
3. 타입이나 태그가 다르면 교체로 판단한다
4. 텍스트 노드라면 문자열만 비교한다
5. 같은 엘리먼트라면 속성을 비교한다
6. 자식 배열을 비교하여 추가, 삭제, 재정렬 여부를 계산한다

즉 Diff는 전체를 다시 만드는 것이 아니라, **변경 종류를 잘게 나누어 Patch 목록으로 분해하는 과정**입니다.

## 8. 최소 변경을 찾기 위한 5가지 핵심 케이스

이 프로젝트의 Diff는 아래 5가지 핵심 케이스를 중심으로 동작합니다.

### 1. 생성 (`CREATE`)

이전 트리에는 없고 새 트리에만 있는 노드는 새로 생성해야 합니다.

### 2. 삭제 (`REMOVE`)

이전 트리에는 있었지만 새 트리에는 없는 노드는 제거해야 합니다.

### 3. 교체 (`REPLACE`)

노드 타입이나 태그가 달라지면 기존 노드를 재사용할 수 없으므로 교체합니다.

예:

- `div` -> `span`
- `text` -> `element`

### 4. 텍스트 / 속성 변경 (`TEXT`, `ATTR_SET`, `ATTR_REMOVE`)

같은 노드라면 노드 자체를 유지하고, 텍스트 내용이나 속성만 변경합니다.

예:

- `"Hello"` -> `"Hello World"`
- `class="a"` -> `class="b"`

### 5. 형제 노드 재정렬 (`REORDER_CHILDREN`)

같은 부모 아래 자식 순서가 바뀌면, 형제 노드 목록을 비교하여 순서 변경 Patch를 생성합니다.

이 과정에서 `key`가 매우 중요합니다.

## 9. key를 사용하는 이유

리스트나 형제 노드를 비교할 때 `key`가 없으면 순서가 바뀐 경우에도 같은 노드를 안정적으로 식별하기 어렵습니다.

그 결과:

- 기존 노드를 재사용하지 못하고
- 불필요한 삭제 / 생성이 늘어나고
- 상태 유지가 어려워질 수 있습니다

이 프로젝트는 `data-key`, `key`, `id` 등을 기준으로 비교 키를 생성하여 다음을 수행합니다.

- 같은 노드인지 식별
- 리스트 순서 변경 추적
- `REORDER_CHILDREN` Patch 생성
- 재정렬 상황에서 기존 노드 재사용 또는 subtree 재구성

즉 `key`는 단순한 속성이 아니라, **리스트 diff 정확도와 실제 DOM 변경량을 줄이는 핵심 장치**입니다.

## 10. Patch 타입

이 프로젝트에서 구현한 주요 Patch 타입은 다음과 같습니다.

- `CREATE`: 새 노드 생성
- `REMOVE`: 기존 노드 삭제
- `REPLACE`: 노드 교체
- `TEXT`: 텍스트 변경
- `ATTR_SET`: 속성 추가 / 변경
- `ATTR_REMOVE`: 속성 삭제
- `REORDER_CHILDREN`: 자식 순서 변경

즉 Diff 결과는 단순히 "다르다"가 아니라, **어떻게 바꿔야 하는지에 대한 구체적인 작업 지시서**로 바뀝니다.

## 11. Diff 결과를 실제 DOM에 반영하는 방법

Diff가 끝나면 Patch 목록이 만들어집니다. 그 다음 단계는 이 Patch를 실제 DOM에 적용하는 것입니다.

이 프로젝트는 Patch를 다음 순서로 실제 DOM에 반영합니다.

- 삭제
- 텍스트 / 속성 / 교체
- 생성
- 재정렬

이렇게 하면 경로 충돌을 줄이고, 최소 변경 방식으로 실제 DOM을 안정적으로 업데이트할 수 있습니다.

즉 실제 DOM은 마지막 단계에서만 수정되며, 비교와 판단은 그 전에 모두 Virtual DOM에서 수행됩니다.

## 12. React에서 실제 DOM을 변경할 때, Virtual DOM과 Diff 알고리즘의 동작 방식

React 스타일 렌더링의 핵심 흐름은 다음과 같습니다.

1. 상태(state)나 props가 변경된다
2. 컴포넌트가 다시 실행된다
3. 새로운 Virtual DOM 트리가 생성된다
4. 이전 Virtual DOM과 새 Virtual DOM을 Diff 알고리즘으로 비교한다
5. 변경된 부분만 Patch 형태로 계산한다
6. Patch만 실제 DOM에 반영한다

즉 React는 실제 DOM을 직접 비교하는 것이 아니라, **이전 Virtual DOM과 새로운 Virtual DOM을 비교해서 실제 DOM 변경량을 최소화**합니다.

이 프로젝트는 바로 이 과정을 Vanilla JavaScript로 직접 구현한 것입니다.

## 13. Demo Lab에서 검증하는 내용

Demo Lab은 과제 요구사항을 직접 검증하는 페이지입니다.

주요 흐름:

- 실제 영역과 테스트 영역이 따로 존재
- 페이지 로드 시 실제 영역의 샘플 HTML을 VDOM으로 변환
- 변환된 VDOM으로 테스트 영역 렌더링
- 사용자가 테스트 영역 HTML 수정
- Patch 버튼 클릭 시 Diff 결과만 실제 영역에 반영
- 변경된 VDOM은 History에 저장
- Undo / Redo로 특정 상태 복원
- VDOM 트리 구조 시각화
- Patch 후 변경 노드 하이라이트

즉 Demo Lab은 **실제 DOM -> VDOM 변환 -> Diff -> Patch -> History**가 올바르게 동작하는지 검증하는 학습용 / 테스트용 페이지입니다.

## 14. Benchmark에서 검증하는 내용

Benchmark는 공용 라이브러리를 기준으로 VDOM 방식과 직접 DOM 조작 방식을 비교하는 성능 실험 페이지입니다.

여기서 확인하는 포인트는 다음과 같습니다.

- 같은 데이터 구조를 기준으로 두 방식이 어떻게 렌더링되는지
- 변경량이 적을 때 VDOM의 장점이 어떻게 드러나는지
- 노드 수가 많아질 때 직접 DOM walk와 어떤 차이가 나는지
- diff + patch 전략이 실제 DOM 변경량을 줄이는지

즉 Benchmark는 **"Virtual DOM이 왜 필요한가"를 개념이 아니라 실험 결과로 보여주는 도구**입니다.

## 15. 프로젝트 핵심 메시지

이 프로젝트는 React 전체를 복제한 것이 아니라, **Fiber 도입 이전 React의 핵심 아이디어를 Vanilla JS로 구현한 프로젝트**입니다.

핵심 메시지는 세 가지입니다.

1. 실제 DOM을 바로 계속 건드리지 않고, 먼저 Virtual DOM에서 비교한다.
2. Diff 알고리즘으로 바뀐 부분만 찾는다.
3. Patch만 실제 DOM에 반영하여 최소 변경 렌더링을 수행한다.

즉 우리가 구현한 라이브러리는 **브라우저 DOM 이해 -> Virtual DOM 생성 -> Diff -> Patch -> key 기반 비교 -> 실제 DOM 반영**까지 이어지는 전체 흐름을 직접 보여주는 구조입니다.
