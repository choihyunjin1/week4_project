# Week4 Team3 Project

HTML, CSS, Javascript(Vanilla)로 **Virtual DOM 라이브러리**를 직접 구현하고, 이를 검증할 수 있는 Demo page와 Benchmark 페이지를 만든 프로젝트를 진행하였습니다.

이 프로젝트의 목적은 단순히 개념을 정리하는 것이 아니라, 브라우저의 실제 DOM이 어떻게 동작하는지 이해하고, 그 위에서 Virtual DOM과 Diff 알고리즘이 왜 필요한지 직접 구현과 실험을 통해 확인하는 데 있습니다.

## 1. 프로젝트가 다루는 핵심 주제


- `브라우저는 DOM을 어떻게 다루는가`
- `실제 DOM은 왜 비용이 큰가`
- `Virtual DOM은 어떤 구조를 가지는가`
- `왜 Virtual DOM이 필요한가`
- `Diff 알고리즘의 동작 방식이 어떻게 되는가`

## 2. 역할 분담
1. Virtual DOM / Diff 알고리즘이 적용된 웹페이지를 각자 구현한 후 하나로 통합했습니다.

2. Demo page에서는 실제 영역과 테스트 영역을 두고 Virtual DOM 생성, Diff, Patch, Undo / Redo 흐름을 직접 확인할 수 있도록 구현했습니다.

3. Benchmark 성능 검증은 각각 구현한 작업물들을 합친 후 적용하였습니다. 
   Virtual DOM 방식과 Real DOM 조작 방식을 동시에 주입하여 두 방식의 처리 시간과 DOM 갱신 비용을 비교할 수 있도록 구현했습니다.
   
## 3. 실제 DOM이 느린 이유

실제 DOM은 브라우저 렌더링 엔진과 연결된 구조입니다.

즉 DOM을 직접 수정하면 브라우저는 화면을 다시 계산해야 할 수 있고, 이 과정에서 비용이 커집니다.

### Reflow
크기나 위치 변화로 레이아웃을 다시 계산하는 과정이라 비용이 큽니다.

### Repaint
위치 변화 없이 색상, 배경 같은 시각 정보만 다시 그리는 과정입니다.

따라서 이러한 과정들을 자주 직접 수정하면 브라우저 부담이 커져 성능 저하가 발생할 수 있습니다.

## 4. Virtual DOM

### Virtual DOM이란

Virtual DOM은 실제 DOM을 메모리 위에서 표현한 **자바스크립트 객체 트리**입니다.

### 이 프로젝트의 VDOM 구조

이 프로젝트에서 Virtual DOM 노드는 다음과 같은 정보를 가집니다.

- `type`: `element`, `text`
- `tag`: 예: `div`, `article`, `button`
- `attrs`: 속성 정보
- `children`: 자식 노드 배열
- `text`: 텍스트 노드 값
- `key`: 형제 노드 비교용 식별자
- `path`, `depth`: 트리 시각화와 patch 추적용 메타데이터

즉 Virtual DOM은 단순히 HTML 문자열이 아니라, 비교와 추적이 가능한 구조화된 객체 트리입니다.

## 5. Virtual DOM이 필요한 이유

### 1. 실제 DOM을 직접 계속 수정하지 않기 위해

### 2. 이전 상태와 새 상태를 비교하기 쉽게 만들기 위해

### 3. 최소 변경 렌더링을 하기 위해

전체 화면을 다시 그리는 대신, 바뀐 부분만 찾아 실제 DOM에 반영할 수 있습니다.
즉 Virtual DOM은 **실제 DOM을 대체하는 것이 아니라, 실제 DOM을 효율적으로 업데이트하기 위한 중간 비교 구조**입니다.

## 5. Diff 알고리즘

Diff 알고리즘은 **이전 Virtual DOM**과 **새로운 Virtual DOM**을 비교하여 변경된 부분만 찾아내는 알고리즘입니다.

### Diff 알고리즘을 사용하는 이유

- 실제 DOM 전체를 다시 그리는 비용을 줄이기 위해
- 변경되지 않은 노드는 재사용하기 위해
- 새로운 노드, 삭제된 노드, 순서 변경된 노드를 정확히 식별하기 위해
- 최소 변경 렌더링을 수행하기 위해

## 6. Diff 알고리즘의 동작 방식

이 프로젝트의 Diff 알고리즘은 두 VDOM 트리를 비교하여 최소 변경 목록을 찾습니다.

기본 흐름은 다음과 같습니다.

1. 이전 노드와 새 노드를 비교한다
2. 노드가 없으면 생성 또는 삭제로 판단한다
3. 타입이나 태그가 다르면 교체로 판단한다
4. 텍스트 노드라면 문자열만 비교한다
5. 같은 엘리먼트라면 속성을 비교한다
6. 자식 배열을 비교하여 추가, 삭제, 재정렬 여부를 계산한다


## 7. key를 사용하는 이유

리스트나 형제 노드를 비교할 때 `key`가 없으면 순서가 바뀐 경우에도 같은 노드를 안정적으로 식별하기 어렵습니다.

즉 `key`는 단순한 속성이 아니라, **리스트 diff 정확도와 실제 DOM 변경량을 줄이는 핵심 장치**입니다.


## 8. Demo page에서 검증하는 내용

Demo page는 실제 DOM -> Virtual DOM 변환, Diff 계산, Patch 적용, History 이동을 직접 눈으로 확인하는 검증 페이지입니다.

여기서 확인하는 포인트는 다음과 같습니다.

- 실제 영역과 테스트 영역이 각각 어떻게 유지되는지
- 테스트 영역을 수정했을 때 어떤 변경점이 발생하는지
- Patch 버튼을 눌렀을 때 변경된 부분만 실제 영역에 반영되는지
- 뒤로가기 / 앞으로가기 버튼으로 이전 Virtual DOM 상태를 복원할 수 있는지

즉 Demo page는 **"Diff와 Patch가 실제로 어떻게 동작하는가"를 시각적으로 보여주는 도구**입니다.

## 9. Benchmark에서 검증하는 내용

Benchmark는 공용 라이브러리를 기준으로 VDOM 방식과 직접 DOM 조작 방식을 비교하는 성능 실험 페이지입니다.

여기서 확인하는 포인트는 다음과 같습니다.

- 변경량이 적을 때와 많아질 때 Virtual DOM과 Real DOM의 지연시간이 어떻게 나타나는지

즉 Benchmark는 **"Virtual DOM이 왜 필요한가"를 개념이 아니라 실험 결과로 보여주는 도구**입니다.

## 10. 회고

이번 프로젝트를 진행하면서 가장 크게 느낀 점은 HTML과 DOM이 단순한 마크업이 아니라 **트리 구조의 자료구조**라는 점이었습니다.
평소에는 화면을 구성하는 태그 정도로만 보였지만, 직접 Virtual DOM을 만들고 경로(path), depth, children 구조를 다루다 보니
자료구조 시간에 배웠던 트리, 순회, 비교, 재정렬 같은 개념이 실제 프론트엔드 구현에서 그대로 사용된다는 점을 체감할 수 있었습니다.

또 하나의 인사이트는 **Virtual DOM이 항상 최적의 해답은 아니라는 점**이었습니다.
처음에는 Virtual DOM이 무조건 더 좋은 기술이라고 생각했지만, Benchmark를 통해 변경량이 적은 경우와 많은 경우,
그리고 단순한 직접 DOM 조작이 더 직관적이거나 유리할 수 있는 경우도 확인할 수 있었습니다.
즉 중요한 것은 특정 기술 자체를 절대적으로 보는 것이 아니라,
현재 문제의 구조와 변경 패턴에 따라 어떤 방식이 더 적절한지 판단하는 것이라는 점을 배울 수 있었습니다.

결국 이번 프로젝트는 Virtual DOM과 Diff 알고리즘을 구현해보는 것에서 끝난 것이 아니라,
브라우저 위에서 자료구조와 알고리즘이 실제로 어떻게 쓰이는지,
그리고 성능 최적화 역시 상황과 맥락에 따라 달라진다는 점까지 이해할 수 있었던 작업이었습니다.
